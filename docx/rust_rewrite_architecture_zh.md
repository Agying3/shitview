# shitview Rust 重构技术决策与开发铺垫

更新时间：2026-08-09
项目：`shitview`

## 1. 文档目的

这份文档用于记录 shitview 从当前 Python + PySide6 原型迁移到 Rust 高性能桌面应用的背景、判断、目标和实施边界。

它不是一份空泛的技术选型报告，而是后续开发时的共同基线：

- 说明现有项目已经完成了什么；
- 说明当前为什么卡顿、为什么视觉和动画不够成熟；
- 记录为什么最终倾向 Rust，而不是 C++；
- 明确 1TB 大目录和上千、上万子目录场景下的产品目标；
- 规定 Rust 版本不应机械翻译 Python，而应重做数据流和渲染模型；
- 将迁移拆成可以逐步验证的阶段，避免一次性重写后失去参照物。

后续所有实现都应优先遵守本文件中的架构边界和性能目标。若实现与本文冲突，应先更新决策记录，再继续编码。

## 2. 项目定位

shitview 是一个面向本地项目目录的动态文件夹地图工具。它希望把普通的文件系统树转换成可以浏览、缩放、拖动和观察变化的视觉化项目地图。

核心使用场景不是单纯列出文件，而是帮助用户回答：

- 一个项目有哪些主要模块；
- 模块之间的目录层级如何组织；
- 哪些文件是目录中的核心节点；
- 最近哪些路径发生了变化；
- 在一个很大的项目中，如何快速定位某个模块或文件。

因此，产品同时包含三个问题：

1. 文件系统索引：可靠地发现目录和文件的变化。
2. 结构模型：把海量文件转换成适合浏览的层级和摘要。
3. 图形交互：在不牺牲流畅度的前提下提供缩放、平移、展开、筛选和动画。

这三个问题不能混成一个 UI 刷新函数。后续 Rust 版本必须将索引、视图模型和渲染层分离。

## 3. 当前 Python 原型基线

当前仓库是一次初始原型和重命名过程中的工作树。原项目名称曾为 `peep_hole_pro`，当前包名已经改为 `shitview`，但 Git 工作树仍然存在 staged 和 unstaged 混合状态。

当前代码的主要层次如下：

```text

├── plugin.py

│   ├── models.py

    ├── graphics_view.py
    ├── theme.py
    └── view_model.py
```

现有 Python 版本已经具备以下功能：

- `python -m shitview.main <folder>` 启动入口；
- `shitview` 包的 `analyze_folder`、`summarize_folder`、`open_shitview` API；
- 目录扫描和 `FileTreeSnapshot` 快照模型；
- 快照 diff，支持 added、removed、modified 和 label_changed；
- `.shitview/labels.json` 标签规则持久化；
- `.shitview/layout.json` 用户拖动位置持久化；
- 基于轮询的目录变化监听；
- 图节点、目录分组、正交连线和基础避障；
- 节点拖动、父节点带动子节点、鼠标悬停放大；
- 右侧详情和变更活动面板；
- 无边框暗色 Qt 主窗口。

因此，Rust 版本不是从零构想产品，而是要以 Python 版本作为行为参考和功能清单。

## 4. 当前原型的主要问题

### 4.1 扫描上限存在实际缺陷

`FileSystemScanner` 在递归前根据当前节点数量计算剩余值，但递归进入子目录后没有再次强制限制总节点数。

当前代码位于：

- `src/shitview/services/scanner.py:42-44`

实际验证中，设置 `max_nodes=10` 仍然可以得到 18 个节点。说明当前上限不是全局上限，只是当前目录层级的枚举提示。

这会导致：

- 大目录扫描量超过预期；
- 目录大小是部分子树的大小；
- 子目录数量可能与可见节点数量不一致；
- 用户不知道地图是否被截断；
- 后续布局性能保护失效。

Rust 版本不能把“截断”隐藏在扫描器内部。扫描结果必须明确记录：

```text
scanned_nodes
visible_nodes
omitted_nodes
is_truncated
truncation_reason
```

### 4.2 当前监听是全量轮询

`PollingFolderWatcher` 每个间隔都会执行完整的 `os.walk`，计算所有路径、文件大小和修改时间的指纹。发现变化后，`ShitviewEngine.refresh()` 又会完整扫描一次目录。

主要代码位于：

- `src/shitview/services/watcher.py:36-58`
- `src/shitview/services/engine.py:31-37`

这意味着一次文件修改至少可能产生两轮全目录访问：

```text
完整指纹扫描 -> 发现变化 -> 完整快照扫描 -> 完整布局 -> 完整场景重建
```

小目录可以接受，大目录会产生明显的 CPU、磁盘和 UI 延迟。

此外，扫描器和监听器的忽略目录列表并不完全一致，缓存目录可能触发无意义刷新。

### 4.3 刷新不是串行调度

主窗口会在线程中启动引擎，而 watcher 也会在自己的线程调用刷新：

- `src/shitview/ui/main_window.py:283-287`
- `src/shitview/services/engine.py:31-37`

当前没有刷新锁、任务队列或 generation 检查，因此在扫描较慢时可能出现：

- 两次扫描交错执行；
- 新快照被旧快照覆盖；
- changes 事件顺序错乱；
- 打开新目录后旧引擎事件晚到，污染当前界面。

Rust 版本必须采用单一索引任务队列。任何时刻只允许一个快照提交者，旧任务可以取消，也可以通过 generation 丢弃结果，但不能直接并发写入当前模型。

### 4.4 UI 每次变化都重建整张图

`MapCanvas.render_snapshot()` 的流程是重新创建场景、背景、节点、分组、连线，再调用 `fitInView()`：

- `src/shitview/ui/canvas.py:18-37`

这不是增量渲染，而是全量重建。

一个文件发生变化时，理想流程应当只更新受影响的节点、祖先摘要、变化标记和必要的布局区域；当前实现会把所有图元重新创建。

### 4.5 图元数量和连线避障放大了成本

每个节点并不是单个绘制对象，节点包含路径、色条、顶部高光、标题和元信息等多个子图元。每条边也是独立的 `QGraphicsPathItem`，并且在更新路径时需要检查其他节点矩形。

主要代码位于：

- `src/shitview/ui/graph_items.py:107-196`
- `src/shitview/ui/graph_items.py:199-380`
- `src/shitview/ui/canvas.py:146-161`

当前项目有 44 个节点、43 条边时，边与节点的潜在障碍物检查已经达到约 1800 次。按 500 个节点粗略估算，完整重建一次可能接近 25 万级别的边-节点检查，还不包括 Qt 图元创建、文字绘制和碰撞处理。

这说明当前卡顿主要是渲染架构问题，不是简单的 Python 语法速度问题。

### 4.6 全场景缩放会牺牲可读性

当前在渲染后对整个 `scene.itemsBoundingRect()` 进行 `fitInView()`。背景面板覆盖整个布局区域，因此布局越宽，所有节点就会被缩得越小。

代码中虽然存在 `_viewport_rect()` 和 `_readable_focus_rect()`，但它们没有被真正用于初始化视角：

- `src/shitview/ui/canvas.py:33-37`
- `src/shitview/ui/canvas.py:163-189`

Rust 版本应采用多级细节和视口渲染：

- 远景显示模块摘要；
- 中景显示目录和重要文件；
- 近景显示完整文件名、标签和元数据；
- 只有视口附近的对象参与详细绘制和动画。

## 5. 为什么考虑 Rust

考虑 Rust 不是为了追求语言标签，而是为了满足以下工程目标：

- 目录索引需要长期后台运行而不拖慢 UI；
- 多线程扫描、监听、数据库提交和渲染数据准备需要明确边界；
- 大目录索引需要控制内存，不把所有对象都变成高成本 UI 对象；
- 图布局、空间索引、增量 diff 和可见性筛选需要稳定执行；
- Windows 桌面应用希望有可控的单文件发布和较低运行时依赖；
- 需要获得比当前 PySide6 图元模型更高的动画和渲染上限。

Rust 对本项目还有一个实际优势：用户主要使用 Vibe Coding，AI 对 Python 和 Rust 的生成、解释、重构和错误修复能力更适合当前工作方式。C++ 虽然性能上限很高，但会引入更多 AI 协作成本：指针、所有权、Qt 对象生命周期、moc、CMake、MSVC、模板和 ABI 问题都可能降低迭代速度。

因此，技术上可以选择 C++，但实际开发效率和维护风险使 C++ 不适合作为当前项目的第一选择。

Rust/C++ + QGraphicsView

## 7. 目标定义

### 7.1 远期目标

在本地 SSD 上，对 1TB 级目录进行后台索引，目录包含上千甚至上万子目录时，界面仍保持可操作，平移、缩放和局部动画流畅。

这里的“流畅”不是一次性把所有文件画出来，而是：

- 应用打开后尽快显示根目录和一级摘要；
- 后台索引持续进行，UI 不阻塞；
- 用户展开哪个模块，哪个模块才生成更细的节点；
- 当前视口内对象保持稳定帧率；
- 文件变化只更新受影响区域；
- 索引可以暂停、取消和恢复。

### 7.2 不应承诺的目标

以下目标不现实，也不应作为产品承诺：

- 1TB 目录中的所有文件同时以完整卡片显示；
- 百万级文件全部同时带动画；
- 百万级文件之间全部画连线；
- 首次打开时同步完成全盘扫描；
- 在网络盘、机械硬盘和极慢权限环境下保证固定扫描时间。

容量本身不是唯一变量。真实性能还取决于文件总数、目录深度、磁盘类型、杀毒软件、权限、符号链接和是否为网络路径。

### 7.3 建议性能指标

| 指标 | 目标 |
|---|---:|
| UI 输入响应 | 小于 16ms |
| 平移/缩放 | 目标 60 FPS |
| 首次启动反馈 | 200ms 内显示根目录或加载状态 |
| 首屏摘要 | 1 秒内出现 |
| 索引线程 | 不阻塞 UI 线程 |
| 可见节点 | 首期 2,000，远期 10,000 |
| 单次增量提交 | 100ms 级别 |
| 变更防抖 | 100-300ms 合并一批 |
| 索引暂停 | 可取消，退出时可恢复 |
| 内存 | 不随 1TB 容量线性增长 |

这些数字是工程目标，不是未经基准测试的保证。正式发布前必须在真实目录上测量并记录。

## 8. 推荐技术路线

推荐从 Rust 开始，但不建议一开始就做复杂的 Python-Rust FFI。第一阶段建立独立 Rust 版本，用文件快照和测试结果与 Python 原型进行对照。

推荐组合：

```text
Rust
├── jwalk 或 ignore：并行目录扫描
├── notify / Windows ReadDirectoryChangesW：增量监听
├── rusqlite：索引数据库和 WAL
├── serde / serde_json：快照、配置和调试导出
├── rayon 或 tokio：后台任务，按实际模型选择
└── Slint：原生应用外壳、控件、主题和动画
```

### 8.1 为什么首选 Slint

- 纯原生桌面 GUI，不依赖 WebView；
- 声明式组件、状态、属性绑定和动画适合精修桌面界面；
- 主窗口、工具栏、设置、检查器和主题可以保持统一；
- Rust 绑定直接，适合当前 Vibe Coding 协作方式；
- Windows 优先开发，同时可保持 Linux 和 macOS 的架构边界；
- 可以让 Slint 负责应用外壳，把大规模图谱交给自定义批量画布。

Slint 不能通过“每个文件一个完整 UI 组件”的方式承担 10,000 节点目标。图谱必须使用视口裁剪、LOD 和批量绘制，节点、连线与动画只处理当前可见数据。

### 8.2 自定义画布与性能回退

产品主线固定为 Slint。Phase 0 先验证 Slint 原生窗口和合成节点场景，再验证自定义画布接入。若 Slint 组件式图谱无法达到目标，不更换应用外壳，而是把画布实现替换为 Rust 自定义 GPU 渲染层。egui/wgpu 仅可作为隔离的性能对照，不是产品主 UI。

## 9. Rust 目标架构

```text
┌──────────────────────────────────────┐
│              Rust UI                  │
│  Canvas / Inspector / Toolbar / UX    │
└──────────────────┬───────────────────┘
                   │ RenderSnapshot / Commands
┌──────────────────▼───────────────────┐
│          View Model / Projection       │
│ expand, collapse, filter, LOD, visible │
└──────────────────┬───────────────────┘
                   │ Query / Update
┌──────────────────▼───────────────────┐
│             Project Core               │
│ snapshot, diff, labels, layout, index │
└──────────────┬───────────────┬────────┘
               │               │
┌──────────────▼──────┐ ┌──────▼─────────────┐
│ Background Indexer    │ │ File Watcher       │
│ parallel scan + DB    │ │ native incremental │
└───────────────────────┘ └────────────────────┘
```

### 9.1 Indexer

Indexer 负责发现文件系统事实，不负责 UI 排版。

每个文件或目录至少需要保存：

```text
id
parent_id
path 或 path_id
name
kind
depth
size
mtime
child_count
subtree_file_count
subtree_size
flags
```

索引器必须支持：

- 并行扫描；
- 权限失败和文件消失；
- 符号链接策略；
- 忽略规则；
- 任务取消；
- 进度上报；
- 扫描 generation；
- 增量变更提交。

不应把一整个超大目录树直接建成拥有大量字符串副本的内存对象。应使用数据库、字符串池、ID 和按需查询，必要时只将当前展开路径载入内存。

### 9.2 File watcher

监听器负责产生原始文件变化事件，不负责直接刷新 UI。

推荐流程：

```text
OS change event
    -> debounce
    -> normalize path
    -> coalesce events
    -> index update queue
    -> affected ancestor summary update
    -> view projection update
```

监听器异常必须变成可见状态：

- 监听暂时失败；
- 目录被删除；
- 权限发生变化；
- 需要重新扫描；
- 当前内容可能过期。

### 9.3 View Model

View Model 是整个迁移中最重要的层。它把“索引中存在的海量对象”投影成“当前用户需要看到的少量对象”。

需要包含：

- 展开/折叠状态；
- 当前选中路径；
- 标签筛选；
- 文件类型筛选；
- 重要模块筛选；
- 当前搜索结果；
- 视口范围；
- LOD 级别；
- 被截断的数量；
- 当前加载状态。

UI 不应该直接遍历完整索引树。它只能请求当前投影。

### 9.4 Layout Engine

当前 Python 版本大量使用固定宽高、分组岛屿和人工间距。Rust 版本应保留“模块岛屿”的产品感觉，但布局计算要做到：

- 只布局当前展开的节点；
- 布局结果可缓存；
- 节点变化只影响局部区域；
- 不做全图碰撞解算；
- 不让避障算法变成完整图的平方复杂度；
- 拖动时优先保持用户位置，不强行全局推开。

对于边，第一版可以使用简单的层级连线或局部路由。不要在初期追求所有边都绕过所有节点的复杂路径搜索。

### 9.5 Renderer

渲染器不应创建“每个文件一个窗口级对象”的模型。

建议将对象拆成批量数据：

```text
NodeInstance {
    position
    size
    color
    border_color
    state
    label_id
}

EdgeInstance {
    points or source/target
    color
    thickness
    state
}
```

绘制时只提交可见范围和少量预加载范围内的数据。

动画应采用统一时间源和状态：

- hover 动画只影响可见节点；
- 节点位置动画不能触发无穷的全局碰撞；
- 批量刷新时不对每个节点单独启动动画；
- 大数量模式自动降低动画细节；
- 缩放时根据 LOD 切换文字和元数据。

## 10. UI 设计方向

当前电路板风格的问题不是颜色单独不好，而是视觉语言没有形成完整系统：

- 连线太抢视觉注意力；
- 节点、分组和背景层级不够清楚；
- 动画缺少统一的速度、缓动和触发规则；
- 全图视角导致文字缩小；
- 节点信息密度和可读性没有随缩放分级；
- 右侧面板更像调试输出，而不是成熟的检查器。

Rust 版本应先确定 UI 原则：

1. 结构优先：目录层级比装饰连线更重要。
2. 近景优先可读性：文字、标签和元数据显示在用户看得清的距离。
3. 远景优先摘要：远距离只显示模块、数量和变化状态。
4. 动画服务于反馈：新增、删除、选中和展开才使用动画。
5. 大图降级：节点数量越多，阴影、发光、复杂连线和文本越少。
6. 交互稳定：平移、缩放和选择不能因为后台索引突然跳动。

建议保留的视觉方向：

- 暗色背景；
- 模块岛屿；
- 低饱和多色模块标识；
- 轻量电路板式连接线；
- 清晰的目录和文件差异；
- 适度的玻璃、边框和高亮。

建议削弱的内容：

- 大面积背景装饰；
- 每个节点的复杂阴影；
- 不必要的持续动画；
- 远景状态下的完整文件名；
- 所有节点之间都显示的连线。

## 13. 风险与应对

### 风险一：Rust UI 框架不成熟

应对：先做独立画布原型，验证平移、缩放、节点绘制和动画，不要一开始实现全产品。

### 风险二：Rust 编译器导致 Vibe Coding 迭代变慢

应对：

- 采用小模块；
- 优先使用明确的 owned 数据结构；
- 避免过早抽象生命周期；
- 用 `Arc`、`Mutex`、channel 解决第一版工程问题，等行为稳定后再优化；
- 每个阶段保持可编译和可运行。

### 风险三：扫描很快，但显示仍然卡

应对：把扫描和渲染分别基准化。Rust 只解决后台核心，不代表 UI 自动高帧率。必须实现视口裁剪和批量绘制。

### 风险四：全量索引内存过大

应对：使用 SQLite、字符串 ID、按需载入和目录摘要，避免把百万文件全部转成 UI 对象。

### 风险五：过早追求漂亮动画

应对：先完成静态画布和性能基线，之后再加入动画。所有动画都必须有大数量降级策略。

### 风险六：Python 和 Rust 结果不一致

应对：保留 JSON 快照、黄金测试和对照脚本。迁移期间 Python 版本继续作为参考，不直接删除。

## 14. 第一阶段明确范围

Rust 重构的第一个可交付目标应当是：

```text
一个可以 cargo run 的 Rust CLI：

shitview-index <folder> --output snapshot.json
```

它需要完成：

- 扫描目录；
- 应用忽略规则；
- 处理基础异常；
- 输出节点数量和进度；
- 正确执行全局节点上限；
- 导出目录摘要；
- 记录扫描耗时和峰值统计；
- 不依赖 Qt；
- 不阻塞命令行输出。

第二个目标才是最小 Rust 画布。

这样做的好处是，Rust 扫描器和 UI 可以分别验证，任何性能问题都能知道来自索引、布局还是渲染，而不是一次性堆在一个难以调试的桌面程序里。

## 15. 最终决策

当前项目不继续把 Python + PySide6 作为长期产品主线。

最终方向：

```text
Rust 核心 + Rust GPU UI
Slint 原生应用外壳 + Rust 自定义批量画布
Python 版本保留为参考实现和迁移对照
```

不选择 C++ 的主要原因不是 C++ 做不到，而是：

- 当前用户的 AI 协作习惯更适合 Python/Rust；
- C++/Qt 的构建和生命周期问题会显著增加 Vibe Coding 成本；
- Rust 已足以满足扫描、并发、内存和 GPU 渲染需求；
- Rust 版本可以直接重做渲染模型，不需要继续继承当前 Qt 图元设计。

真正的性能目标不是“换语言后自动变快”，而是建立以下数据流：

```text
增量文件事件
    -> Rust 索引
    -> 局部快照变化
    -> 视图投影
    -> 可见节点批量绘制
    -> 仅对可见对象做动画
```

只要遵守这个边界，1TB 目录、上千上万子目录和流畅动画是一个可以认真追求的工程目标；如果继续全量扫描、全量布局、全量重建和全量绘制，换成 Rust 也无法从根本上解决问题。

## 17. 2026-08-09 共同决策基线

本节覆盖前文仍带有候选性质的旧建议。后续实现若与本节冲突，应先更新决策记录。

### 17.1 产品与平台

- 目标用户首先是开发者，核心对象是代码项目；
- 首版 Windows 优先，但核心、索引、存储和 UI 边界保持跨平台；
- 正式应用使用 Rust + Slint，不使用 WebView；
- Python 不进入扫描、数据库、布局或渲染主链路；
- Python 可作为进程外插件能力，第一版只定义稳定 IPC 边界，不交付插件宿主；
- 项目开源，正式发布同时提供安装程序和便携 ZIP。

### 17.2 数据与索引

- 1TB 目录采用两阶段渐进索引：先目录骨架和首屏，再后台补全全部文件；
- 当前视口、展开目录和用户操作拥有更高扫描优先级；
- 大型 SQLite/WAL 索引存放在用户本地应用数据目录；
- `.shitview/` 只保存可移植的小型数据：`project.json`、`layout.json` 和 `labels.json`；
- 本地索引支持固定，未固定索引按容量上限和 LRU 自动清理；
- 依赖分析仅在识别为代码项目时默认开启，并允许关闭；
- 源码只在本地读取，数据库保存依赖边、符号位置和内容哈希，不保存完整源码；
- `.shitviewignore` 用于排除密钥、Cookie、模型、二进制文件和其他敏感路径。

### 17.3 地图、布局与交互

- 基础图层表示目录父子关系；依赖、活动和标签作为可切换图层；
- 使用目录层级、自动 LOD 和手动固定的混合模式；
- 已有节点尽量不移动，新增节点在父目录附近局部插入，全局重排只能由用户显式触发；
- 可见节点目标为 1,000-10,000；1,000-5,000 节点目标 60 FPS，10,000 节点最低目标 30 FPS 且交互不冻结；
- 保留并精修暗色电路板风格，绿色正交连接线不能互相重合，节点、模块和文件不能互相重叠；
- 后续可增加其他暗色或浅色主题，但不能影响第一版主线；
- 单击节点可在检查器中只读预览源码，编辑由可配置外部编辑器完成，并支持跳转到行列。

### 17.4 开发与验收

- 首个正式版本覆盖完整产品闭环，但内部必须按可运行里程碑逐步交付；
- Phase 0 验证 Slint 依赖、合成节点画布、SQLite/WAL 和真实 GUI；
- Phase 1 完成渐进索引、任务取消、进度、generation 和 SQLite 提交；
- Phase 2 完成 LOD、展开折叠、稳定局部布局和视口裁剪；
- Phase 3 完成增量监听、搜索、标签和活动图层；
- Phase 4 完成依赖图层、只读源码预览、动画和视觉精修；
- Phase 5 完成真实 GUI 测试、性能报告、安装程序和便携发布包；
- 多会话开发使用独立 worktree，分别负责 Core、Slint 和 Benchmark，由主会话集成；
- Python 原型冻结为参考行为，不再增加产品功能。
